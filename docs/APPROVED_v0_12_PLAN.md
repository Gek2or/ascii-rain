## Производственный план на базе v0.11

**Статус: план реализации, а не новая сборка игры.** В этой работе прочитан исходный ZIP v0.11 и отчёт о нём; существующий проект не изменён. ## 1. Обещание игроку и границы версии

После выхода из Arrival Node игрок видит не равномерное поле зданий, а несколько районов с узнаваемой архитектурой. В них есть улицы под мостами, доступные галереи, ограниченная сеть крыш и один настоящий нижний технический маршрут. В каждой боевой локации можно выбрать путь и понять, откуда придёт опасность. Город продолжает работать сам: дроны обслуживают инфраструктуру, табло меняются, по дальней эстакаде проходит транспорт, из вентиляции выходит пар.

Ключевой принцип: **добавляем места и связи между ними, а не только количество мешей**. Сохраняем существующую площадь города; не увеличиваем расстояние между интересными местами ради размера карты.

Неизменяемые правила:

- Godot, полноценный 3D third-person action roguelike, ПК и Android.
- ASCII остаётся основным способом изображения. Сохраняем исправления v0.10.1/v0.11; не пересобираем шейдер в рамках городского прохода.
- Ночное пространство, тёплые локальные источники, нейтральные читаемые поверхности, тёмный дальний план. Основа — оба утверждённых файла в `reference/`, не новый случайный стиль.
- Далёкое альтернативное будущее 2500–2800. Нормальная 3D-реальность возникает только в редких значимых артефактах и предусмотренных сюжетом встречах. Не заполняем улицы «настоящими» людьми.
- Рабочий цикл: стартовый предмет → два разных района → событие телепортера и WATCHER → необязательная находка → выход. Полный обход шести зон не становится обязательным.
- Существующие настройки, управление, музыка, предметы, сохранения и постоянный архив не сбрасываем.

В v0.12 не включаем: управляемый транспорт; население с экономикой; все открываемые здания; полное разрушаемое окружение; динамический лифт с боем на нём; лазающих по отвесной лестнице мобов; новый класс врагов или второго босса. Это отдельные системы, а не декор.

## 3. Планировка и стабильные идентификаторы

Начальные центры ниже взяты из текущего `EncounterDirector`, в мировых координатах Godot. Они служат привязками к существующему городу, не утверждёнными границами новых мешей. Габариты сначала проверяются простой геометрией.

| Зона | Технический ID / центр | Новая роль |
|---|---|---|
| Arrival Node | `arrival` / (0, 0, 8) | Спокойное прибытие, первый предмет, понятные направления выхода |
| Market Ruins | `market_ruins` / (45, 0, 43) | Торговые ряды, внутренний двор, галерея над ним |
| Transit Spine | сохранить `signal_concourse` / (0, 0, 65) | Нижний распределительный зал и верхняя транспортная платформа |
| Archive Stacks | сохранить `archive_row` / (50, 0, -20) | Архивный двор, антресоль, доступный служебный верхний ярус |
| Memory Gardens | `memory_gardens` / (-45, 0, 44) | Террасы, павильон, искусственный сад, открытый бой |
| Utility Depths | сохранить `utility_spine` / (-52, 0, -18) | Технический двор и локальный нижний проход |
| Rooftop Relay | новая подзона `rooftop_relay`, родитель `archive_row`; точка входа уточняется | Две-три связанные крыши на стороне архивного района, дополнительный подход к северной части |
| Null Terminal | `null_terminal` / (0, 0, -64) | Сохранённая наземная арена WATCHER и выхода |

Шесть новых архитектурных характеров — пять преобразуемых районов плюс Rooftop Relay. Arrival и арена остаются отдельными опорными точками. Rooftop Relay не выдаёт второе посещение района вслед за Archive Stacks: достижения и `RunProgress` учитывают родительский ID, а не число этажей.

Предлагаемая связность, не чертёж в масштабе:

```
Arrival -> Market -> Transit -> Gardens -> Utility -> Null Terminal
   |          |                       |                 |
   +------ Archive <---- street ------+                 |
              +---- Rooftop Relay ---- lower approach ---+
```

Ветки соединяются доступными наземными путями. Верхний обход не позволяет перескочить условия открытия выхода и не открывает стрельбу по WATCHER из безопасного недосягаемого места. Последний подъезд к арене ведёт обратно на её наземный вход.

Город имеет фиксированную связность первого эпизода. Случайность пока применяется к допустимым составам встреч, наградам и несущественному декору, но не к лестнице, без которой ломается весь маршрут. Декоративный RNG отделён от RNG наград/врагов.

## 4. Шесть локаций: архитектура, маршрут, бой, ориентиры

### 4.1 Market Ruins — первый образцовый район

**Вид:** крытый рыночный двор, ряды металлических киосков, глубокие дверные проёмы, частично обрушенный навес, верхняя галерея. Палитра — тёплые лампы и нейтральная бронза, без бесконечного оранжевого свечения каждой детали.

**Маршрут:** широкий наземный обход по краю двора; центральный путь между прилавками; подъём по широкому маршу на галерею около Y=+5.5; второй спуск на противоположной стороне. Верх — полноценная платформа, под которой можно пройти.

**Бой:** сначала два Grunt и один Gunner как тестовая композиция; после прохождения проверок количество меняется director'ом. Стрелок обозначает атаку с галереи, ближние враги идут по своему маршруту. Из любой боевой точки есть уход в сторону; узкие декоративные проходы не становятся ловушками.

**Две точки интереса:** разбитый торговый зал; ремонтный киоск под галереей. Одна ветка содержит потенциальный сундук, другая — более безопасный выход; сундуки не гарантируются во всех точках одновременно.

**Живость:** табло продолжает показывать порядковые номера обслуживания; маленький сервисный дрон обследует щиток вне центральной линии прицеливания.

**Приёмка:** игрок проходит сверху и снизу по одному XZ, враг правильно выбирает лестницу; выстрел не проходит сквозь перекрытие; оба спуска проходимы на сенсорном управлении.

### 4.2 Transit Spine — масштаб и длинные линии обзора

**Вид:** распределительный зал, навесы, две платформы, опоры эстакады, длинные панели указателей, брошенная пассажирская капсула. Не повторять модель Market с другим материалом: здесь преобладают крупные горизонтальные формы.

**Маршрут:** обход у опор на Y=0; платформа около +5.5; короткая переходная часть до +10/+11 только там, где тест позволяет безопасную камеру. Подъёмы с разворотными площадками, не один бесконечный крутой скат.

**Бой:** Gunner создаёт давление с боковой площадки; Tank остаётся на широком доступном пути. Укрытия прерывают длинные линии стрельбы. Попадание не сбрасывает героя с узкой необозначенной кромки.

**Две точки:** сломанная капсула; диспетчерский пост.

**Живость:** далёкий поезд проходит по отдельному недоступному пути, тихо гудят платформы. Поезд — декорация без разрушаемой физики, транспорта и скрытого урона.

### 4.3 Archive Stacks — тайна и тесные дворы

**Вид:** высокие архивные фасады, ниши-индексы, служебные балконы, мост между двумя корпусами, закрытые массивные двери. В доступном полуинтерьере стены имеют глубину и оборотную сторону.

**Маршрут:** двор Y=0, галерея около +5.5, выход на локальный крышный участок. Не каждая башня доступна: закрытые входы визуально отличаются от игровых.

**Бой:** давление Grunt и Skitter, Gunner на явно достижимом втором ярусе. Дверной проём не является местом внезапного спавна на игроке.

**Две точки:** запечатанный архивный шлюз; балкон с неработающим индексатором.

**Сюжет:** резерв под будущую значимую находку, но никаких новых случайных «настоящих фотографий» в каждом шкафу. Существующие артефакты не дублируются ради заполнения локации.

### 4.4 Memory Gardens — пространство и тишина

**Вид:** террасы, искусственные деревья, редкие ветви-кабели, павильон, спокойная геометрия водосборника. Сад не становится ярко-зелёной заливкой; характер передаётся формой и ритмом объектов.

**Маршрут:** большая площадь на Y=0, низкие террасы примерно +2.5/+5.5, мостик к павильону. Больше свободного пространства для бокового движения, чем на рынке.

**Бой:** Skitter заставляет менять направление, редкий Tank занимает широкую ветку. Bomber появляется только при наличии читаемого пространства для выхода из радиуса.

**Две точки:** павильон забытых записей; круг искусственных деревьев.

**Живость:** малые движения крон, символические осадки, звук воды/ветра. Без живых неоцифрованных животных, массовых NPC и навязчивых вспышек.

### 4.5 Utility Depths — настоящий нижний маршрут

**Вид:** технический двор, насосная секция, трубы крупного диаметра, вентиляция, нижняя галерея и небольшой машинный зал. Сначала строим один связный нижний участок, не систему метро под всем городом.

**Маршрут:** Y=0 -> широкий наклонный спуск -> пол около Y=-5 -> второй подъём в соседнюю часть двора. Над частью нижнего маршрута остаётся доступная улица: здесь обязательно одновременно поддержать два этажа.

**Конструкция:** разбить исходную плиту пола на простые части вокруг отверстий. Согласованно исключить в этих областях дорожные меши, мокрые накладки, коллизии и автоматический декор. Под нижней зоной создать собственный пол, стены и ограничение выхода за мир. Нельзя оставлять невидимую коллизию прежнего пола над спуском.

**Бой:** Gunner в открытом машинном зале; Bomber — только в широкой камере с отступлением. Tank не назначается на проход, который не соответствует его габариту.

**Две точки:** насосный узел; ремонтный щит, влияющий только на декоративное состояние до реализации отдельного события.

**Живость:** пар выходит небольшими порциями сбоку от пути; вентиляторы вращаются за решётками. Не использовать густой пар как обязательную маскировку атаки.

### 4.6 Rooftop Relay — высота без игры в прыжки по пикселям

**Вид:** два-три доступных крышных участка с аппаратными блоками, парапетами, антеннами и одной крупной сигнальной мачтой. Фоновый город остаётся недоступным силуэтом, не обещанием зайти на все крыши.

**Маршрут:** широкий подъём из Archive Stacks, две площадки около +10/+11 и +12, два соединяющих мостика, возвратный спуск. Полный обязательный путь проходим без точного прыжка и dash. Удачный прыжок может сокращать расстояние, но не открывать единственный выход.

**Бой:** один-два Gunner в читаемых позициях, ближние враги приходят по доступному мосту. Нет стрельбы из-за пределами игровой дальности и спавнов за спиной прямо на узкой площадке.

**Две точки:** релейная мачта; крыша сервисной станции.

**Живость:** антенна медленно поворачивается, дроны летят выше маршрута. Небо и дальние окна не превращаем в яркий текстовый ковёр.

## 5. Геометрические правила для первой компоновки

Начальные размеры нужно проверить камерой и физическими капсулами, а не считать универсальным стандартом Godot.

| Параметр | Начальная проектная цель |
|---|---|
| Основной боевой коридор | 5–7 м чистой ширины |
| Марш/рампа общего маршрута | 4–5 м; площадка достаточна для разворота камеры |
| Большая площадка боя | примерно 12×12 м и больше по композиции |
| Лёгкий боковой проход | 2.8–3.2 м, при необходимости закрыт для тяжёлого габарита |
| Чистая высота общего пути | не менее 4.8 м для текущего крупного обычного врага плюс проверка реальной формы |
| Уклон основной рампы | ориентир до 25–30°, затем двигательный тест |
| Высота общих верхних этажей | около +5.5 и +11; крыши локально до +12 |
| Нижний этаж | около -5; не глобальное изменение уровня земли |
| Доступ на верхнюю боевую площадку | два независимых выхода без обязательного прыжка |

Лестница получает видимые ступени и подходящую непрерывную коллизию для движения. Прицел, снаряды и камера проверяются отдельно: гладкая коллизия не должна создавать заметную невидимую стену над ступенями. Балконы с маленьким просветом считаются декоративными, а не проходами для Tank.

Сначала крупная форма, потом средняя: колонны, арки, проёмы, карнизы, навесы, перила, оборудование. Мелкие болты и случайные трубы добавляем только после просмотра через ASCII на целевых размерах символа.

## 6. Навигация и director: обязательный фундамент

### Выбранный путь реализации

Для v0.12 сначала расширяем существующий контракт навигации, а не вводим одновременно совершенно новый AI и систему потоковой загрузки. Планируем `LayeredNavigation` на AStar3D с несколькими поверхностями на XZ и явными переходами между ними. AStar3D поддерживает трёхмерные узлы и явные связи [1]; ограничение «одна высота» в этой базе принадлежит нашему сборщику графа.

Навигационные поверхности поставляются вместе с архитектурными модулями. У каждой есть устойчивый `surface_id`, принадлежность району/этажу, границы, допустимые габариты и соединительные точки. Проверки физики подтверждают доступность: одна лишь логическая связь не даёт права пройти сквозь стену.

Сохраняем фасад существующих вызовов `request_route`, `spawn_anchor`, признак готовности, статусы `building/busy/blocked/ok`. Это минимизирует изменения в боевой логике. Детальное разбиение API и адаптера фиксируется до миграции вызывающих файлов.

Приоритеты:

1. Два пола на одном XZ имеют разные узлы и не связываются автоматически по близости.
2. Связь создаётся вдоль реального моста/пандуса, с проверкой опоры и свободного объёма по всей длине.
3. Ближайшая цель выбирается на совместимой поверхности; при прыжке учитывается последняя подтверждённая опора, а не произвольная крыша над игроком.
4. Габариты SMALL/STANDARD/HEAVY фильтруют пути. Не использовать один и тот же результат связности для всех размеров.
5. Запросы распределяются по физическим кадрам, уже полученные пути переиспользуются, недостижимые цели дают временный отказ, а не телепортацию.
6. Нужен тест толпы на узком переходе: очередь/разделение по ширине и ограничение локального заполнения. Глобальное избегание всех со всеми не включаем автоматически.

NavigationRegion3D/navmesh остаётся возможной будущей заменой внутренней реализации, но не обязательной частью этой версии. При таком переходе надо отдельно проверить общие рёбра регионов [2] и допустимые размеры агента. NavigationLink сам по себе не реализует подъём по лестнице, ожидание лифта или прыжок [3]. Поэтому движущиеся платформы и отвесные лестницы исключены из обязательных маршрутов v0.12.

### Многоуровневые встречи

Разделить `district_id` для прогресса забега и `encounter_zone_id` для конкретной площадки. Volume3D определяет этаж и вход, а граф — фактическую связанность. Не создавать вторую волну при каждом шаге через границу объёма: нужны задержка подтверждения входа, временной фильтр выхода и состояние уже начатой встречи.

Budget угрозы сохраняется в рамках района и имеет предел. Переход на галерею не сбрасывает бюджет и не вызывает бесплатное новое вступление. Очистка/отложенные атаки соблюдают паузу, смерть, выход и завершение события как в базе.

Вместо произвольной точки «далеко на XZ» использовать подготовленные spawn anchors с `surface_id`, размером, маршрутной доступностью и проверкой физики. До боя точка проверяется по длине доступного пути, расстоянию, видимости и количеству уже активных врагов; появление рядом сопровождается существующей материализацией. На маленькой крыше не пытаться любой ценой сохранить наземный радиус спавна 27–39 м.

Моб может преследовать на соседний этаж только по реальной связи. Декоративный дрон не входит в боевой каталог. Недоступный противник сверху не должен удерживать локальную встречу навсегда.

## 7. Живость как система, не количество частиц

Три состояния окружения: QUIET, ALERT, RECOVERY. Район может включить тревожный режим после начала настоящего столкновения, а после завершения возвращаться к тихой работе. Смена декоративного состояния не спавнит мобов сама по себе.

Пакет v0.12: сервисный дрон с коротким маршрутом и остановкой; далёкая транспортная капсула; табло с меняющимися строками; медленно поворачивающаяся антенна; вентилятор за решёткой; короткие выбросы пара; редкие искры в безопасной нише; малая локальная область дождя; пространственный фон района.

Для каждой системы задаются максимальное число активных экземпляров, расстояние работы, частота обновления и отдельный выключатель. Объект активируется заранее вне центра экрана, а не появляется в прицеле. Во время паузы все анимации, включая движение шейдерного времени там, где это необходимо, согласованы с игровым временем.

Декоративные лучи и дроны имеют другой силуэт/ритм, чем телеграфы атак. Красные опасные акценты резервируем для боя. Настройка Reduce ambient motion снижает движение окружения и вспышки, не скрывая реальные опасные зоны.

Музыку сохраняем. Новые короткие районные звуки — только собственные/лицензированные с указанием источника; ограниченная полифония, плавное изменение громкости у границ. Выстрелы и предупреждения остаются слышнее фоновых вентиляторов.

## 8. Читаемость ASCII — критерий приёмки мира

Визуальный эталон — `reference/approved_visual_target.png` и `approved_combat_target.png`. Это целевая композиция и настроение, а не доказательство уже достигнутого качества. Сравниваем игровые кадры с одинаковыми камерой и настройками, не выдаём арт за скриншот.

Ближний пол даёт ясную поверхность; навес отделён от неба; между силуэтами есть тёмные промежутки. Входы выделяются формой проёма и локальным источником, а не просто новой вывеской. Кромка платформы обозначается перилом/контрастной гранью, лестница читается геометрией и знаком подъёма. Надпись и цвет не являются единственными подсказками.

Не добавлять glow ко всем новым деталям, не обводить каждую трубу, не возвращать случайные буквы и не осветлять фон ради читаемости одного объекта. Нельзя заставлять пользователя исправлять композицию ползунком яркости после каждой сборки.

Контрольные виды для каждой новой зоны: вход, низ под мостом, верхняя площадка, тёмный проём, бой у яркой вывески, обзор в сторону большого skyline. Снимать с ASCII и временно без него, чтобы разделять дефект формы от дефекта фильтра. Базовые проверки: ПК 1280×720/6 px; мобильный профиль/8 px; крайние поддерживаемые 4 и 10 px проверяются отдельно.

На низком качестве могут исчезнуть болты и декоративный дрон, но не пол, перила опасного края, укрытие, вход или предупреждение атаки. Названия/иконки новой этажности не должны перекрывать прицел и сенсорные кнопки.

## 9. Производительность без ложного «ASCII всё удешевит»

Первый шаг — не выгружать всё подряд, а отделить постоянный игровой каркас от отключаемого декора. Полы, коллизии, критические укрытия, переходы и навигационные связи остаются на месте. Нельзя выгружать мост под игроком/врагом при повороте камеры.

Повторяющийся декор группируется по материалу и пространственной ячейке. Один MultiMesh на целый город не подходит: он рассматривается как один объект при отборе видимости [4]. Продолжаем пространственное разделение существующего detail pass. Видимые дальние сооружения получают укрупнённый вариант по visibility ranges/HLOD [5]; важный проход никогда не исчезает от смены LOD.

Пример стартовых пределов для теста, не характеристики готовой игры:

| Категория | Android Low | Android Medium | ПК High |
|---|---:|---:|---:|
| Декоративные близкие дроны | 1 | 2 | 4 |
| Одновременно активные локальные области пара | 2 | 3 | 6 |
| Новые ближайшие динамические светильники окружения | до 2 | до 3 | до 6 |
| Обновление небоевых состояний | 5 Гц | 5–10 Гц | 10 Гц |
| Выключатель дополнительной живости | Да | Да | Да |

Это ограничения новой подсистемы, а не разрешение добавить столько lights к каждой клетке. Дронам по умолчанию достаточно материала; свет с тенью не назначается на каждый аппарат. Освещение боя имеет приоритет над декоративным.

Путь и связанные спавны ограничиваются по кадру; для возможного navmesh-варианта используются простые источники геометрии, а не весь детальный город [6]. Не обещаем конкретный FPS по одному скриншоту.

Цели профилирования: 60 FPS на выбранном ПК и 30 FPS на Android Medium как первоначальный критерий, при известной модели устройства и фиксированном сценарии. Это бюджеты кадра около 16.7 и 33.3 мс, не уже измеренный результат. Сравнивать медиану/P95/P99 с v0.11 на том же железе, рендерере, сцене и прогретом запуске; мерить также пиковую память и паузы при входе в район. Допустимое ухудшение фиксируется после базового замера, а не подбирается после неудачного теста.

Цель RunGuide на разных этажах: сначала доступный переход «GALERИЯ ↑ / вход 18 м», а потом цель на нужной поверхности. Прямая стрелка в стену или под землю не принимается.

Защищённые подсистемы: текущий шейдер и атласы; сюжетная библия; ID боевых предметов; предметы/оружие/урон; пути настроек и архива; система выбора наград; телепортер/WATCHER. Изменение защищённого файла должно быть отдельно обосновано и покрыто регрессией, а не случайно включено большим рефакторингом.

## 11. Последовательность сборок и проверки перехода

### v0.12a — Working Layers + Market / Transit

Сначала маленький тестовый модуль: два пола на одном XZ, рампа, перекрытие, перила. Затем адаптер навигации, выбор поверхности, spawn anchors и 3D-зоны. После этого Market и Transit строятся крупной простой геометрией. Добавляются один сервисный дрон, одно табло и путь фонового транспорта.

**Готовность:** игрок и два обычных типа врагов проходят сверху/снизу без перепутанного этажа; работает нижний выстрел в верхнего врага при открытой линии; стена/перекрытие блокируют урон; открываются старые сундуки; полный run не заблокирован. Реальный кадр показывает одновременно два доступных маршрута, не только нарисованный мост.

### v0.12b — Archive / Gardens + architectural detail

Добавляем ещё два района и связываем с первыми. Проверяем среднюю геометрию и формы фасадов через существующий ASCII. Подключаем звуковые состояния и ограниченный ambient manager.

**Готовность:** районы различимы без HUD-названия; у каждого есть два маршрута и два ориентира; шаг через границу не перезапускает первую волну; тест чтения силуэта и опасных зон проходит в тени и возле ярких витрин.

### v0.12c — Utility / Rooftop + complete route

Делаем настоящий нижний пол с отверстиями и два пути выхода; локальную сеть крыш. Закрываем границы уровня, восстановление после выхода за мир и подтверждение безопасной опоры. Не переносим WATCHER на крышу; доступ к нему идёт в существующую арену.

**Готовность:** проход над и под одной плитой работает; игрок не падает через выключенный визуальный сектор; враг выбирает этаж цели; ни один тяжёлый моб не назначается в слишком маленький проход; кровля не позволяет безопасно убивать босса вне арены.

### v0.12 RC — Playtest & regression

Сначала тесты логики, затем реальная графика/управление и human playtest. Не объединять результаты разных проверок в надпись «всё проверено».

Обязательные сценарии: улица -> галерея -> другой выход; верхний противник над нижним; движение под мостом; бой через просвет/перекрытие; преследование по рампе; смена этажей в прыжке; вход/выход из района многократно; пауза во время тревоги; сохранение после рестарта; окончание события очищает угрозы; спад FPS не провоцирует уход в неверную поверхность; Android FIRE+drag одновременно с движением на повороте/спуске.

Повторить существующие run-state, items, combat, touch, render pixel и упаковочные проверки v0.11. Результаты предыдущей версии не выдаются за результаты новой. Тесты в dev-template и обычный импорт в стабильный редактор указываются отдельно. Сравнение FPS на программной Mesa не называется тестом телефона.

## 12. Критерии приёмки v0.12

1. Шесть визуально разных зон; старт и арена сохраняют назначение.
2. Двенадцать подготовленных точек интереса; не менее двух в каждой зоне, без обязательной награды в каждой.
3. В нескольких местах есть два проходимых пола над одним XZ, которые различают и игрок, и AI.
4. У каждого обязательного верхнего/нижнего маршрута есть понятный вход и выход без точного прыжка.
5. Мосты, рампы, края, лестницы, герои и опасность читаются в текущем ASCII на ПК и Android-профиле.
6. Декоративные состояния не создают скрытого урона, не имитируют телеграф и выключаются без потери игровой информации.
7. Бой возникает по входу в действительную локацию; районные бюджеты не обнуляются при смене этажа.
8. Предметы, архив, настройки и полный цикл до выхода не регрессировали.
9. Новые тесты имеют фактический результат; неподтверждённые устройства перечислены честно.
10. ZIP включает явные родительские каталоги; проверяются порядок распаковки, безопасные относительные пути, CRC и содержимое.
